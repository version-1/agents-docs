# PR マージリスク評価

スコアは判断用の指標であり、障害の発生確率ではない。評価対象は特定の PR の head/base SHA。評価、採点、出力までを行い、マージ、承認、PR コメント投稿は行わない。

## 手順

1. PR URL/番号とリポジトリを特定する。接続済み GitHub ツールまたは gh で目的、head/base SHA、差分、CI、承認、未解決レビュー、ドラフト・競合状態を取得する。曖昧な対象は確認する。
2. 対象 SHA の実装、呼び出し元、型・API 契約、テスト、設定を読み、影響範囲を追う。PR 本文や CI 成功だけで安全と判断しない。別の作業ツリーのコードを対象 SHA の証拠として扱わない。
3. 下記6項目について、変更に起因する具体的な障害シナリオ、発生条件、根拠、防御策を調べる。複数変更の相互作用も一つのシナリオとして評価する。
4. 判断に必要な検証を実行し、コマンド、対象 SHA、結果を記録する。未実行の検証は理由と判断への影響を記す。必要な情報・検証を取得できない場合は推測で埋めず判定保留にする。無関係なテストを実行できないだけでは保留にしない。
5. 各シナリオを採点する。項目点は所属シナリオの最高点、総合点は6項目の最高点。平均、加算、恣意的な補正はしない。
6. 必須条件を点数と別に確認し、判定を決める。
7. 出力直前に PR の head/base SHA を再取得する。変更があれば差分と証拠を再評価する。安定した対象を取得できなければ判定保留にする。CI・必須条件も最新状態を確認する。
8. [出力契約](references/output.md)を読み、同じ評価結果から Markdown と JSON を出力する。

## 評価項目

- correctness：仕様違反、境界条件、例外、並行処理による不具合。
- security：認可・認証、情報漏洩、入力処理、依存関係の侵害。
- data：データ破損・消失、移行、整合性、復旧可能性。
- performance：遅延、資源枯渇、負荷増加。
- compatibility：API、型、保存形式、既存利用者との互換性。
- operations：配布、設定、監視、切り戻し、障害復旧への影響。

同一シナリオは主な項目に登録し、関連項目から ID を参照する。

## 採点表

| 影響の深刻さ | low | plausible | high |
|---|---:|---:|---:|
| minor：局所的で容易に回復できる | 10 | 20 | 35 |
| moderate：一部機能に支障、回避策あり | 25 | 40 | 55 |
| major：主要機能停止、広範囲への影響 | 51 | 70 | 85 |
| critical：不可逆なデータ消失、重大な侵害 | 75 | 90 | 100 |

- low：具体的な経路はあるが、確認済みの制約・防御策により発生条件が限定される。
- plausible：到達可能な経路と現実的な入力・運用条件があり、有効な防御策を確認できない。
- high：通常の利用条件で発生する根拠、または再現結果がある。
- 深刻さは影響範囲と回復可能性から選ぶ。発生の見込みはコード位置、呼び出し経路、検証結果で説明する。変更行数やテスト数を直接点数にしない。
- 未確認の防御策や予定の修正で点数を下げない。
- 0点は必要な調査を終えて具体的な悪影響を特定しなかった場合。安全を保証しない。
- 情報不足は low や0点に置き換えない。抽象的な懸念だけで major/critical にもしない。
- major は最低51点、critical は最低75点。他項目で相殺しない。

## 判定

必須条件は、必須 CI 成功、競合なし、ドラフトでないこと、リポジトリで要求される承認と未解決レビュー条件の充足。要求がないことを確認できた条件は not_applicable にする。任意 CI を必須と混同しない。成功 CI が対象 SHA に対応することを確認する。

- hold：評価に必要な情報・検証が不足。総合点は null、確認済みのシナリオ点は保持する。
- auto_merge_candidate：評価完了、総合点50以下、必須条件がすべて pass/not_applicable。
- human_review：評価完了だが51点以上、または必須条件が fail/unknown。

必須条件だけが不明なら human_review。安全性評価の情報も不足すれば hold を優先する。候補判定は記録した SHA と確認時点に限り有効。将来の実行処理では SHA と必須条件を再確認する。
