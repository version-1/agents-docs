# 進捗と承認

## GitHub を正本にする

最初にリポジトリ owner/name と default branch を確認し、以後の操作対象を固定する。ゴールごとに管理 issue を1件用意し、本文に達成条件・対象外・子 issue 一覧・依存関係を残す。既存のラベルや Projects は利用できるが、未設定でも本文とコメントだけで再開可能にする。

各作業 issue に次を記録する。

- ゴールの管理 issue、受け入れ条件、成果物の種類。
- 優先度と理由、依存 issue、変更範囲、担当。
- 状態、専用 worktree の絶対パス、branch、PR またはレポートへのリンク。
- base/head SHA、検証コマンドと結果、reviewer の選択・省略理由、指摘と対応。
- 同じ原因に対する改善なしの連続回数、保留理由、解除条件。
- 承認待ちの場合は次節の承認記録。

状態は `ready → implementing → verifying → refining → reverifying → qa → done` を基本とし、修正時は `implementing` に戻す。`awaiting-approval` と `blocked` には元の工程と解除条件を残す。保留は完了ではなく、依存する issue も実行対象から外す。

再開時は管理 issue と子 issue、open/closed PR、マージ状況、worktree・branch・SHA を照合する。記録だけを信じて再実行せず、既存 PR や担当を再利用する。他の実行が同じゴールを処理中なら新たな統括を起動しない。

## 承認記録

人間には実装・検証を済ませた具体的な成果物を提示する。方針決定が先に必要な場合は、選択肢・推奨案・影響を提示し、その判断に依存する作業だけを保留する。

承認待ち1件ごとに、以下を記録する。

- 一意な ID、issue/PR URL、求める判断と必要な理由。
- 選択肢・推奨案、変更範囲・影響、検証結果と未確認点。
- PR なら対象 head SHA と検証対象 base SHA。方針判断なら承認対象の文章。
- 提示日時、承認したユーザーの発言と日時、承認後に実行できる操作。

`/factory approve` は会話上の対象が一意な場合だけ、その1件に適用する。複数ある場合は ID を尋ねる。一括承認や将来の差分への承認として扱わない。重要な変更が入ったら旧承認を失効させ、再提示する。rebase による SHA 変更も再検証し、承認した内容との同一性を示せなければ再承認を求める。

人間承認は品質不合格、失敗した必須 CI、未解決 Medium 以上、上位規則の禁止を免除しない。

## マージと並行統合

1. マージは Pdm/QA がリポジトリ単位で直列化する。後続ブランチの追従が終わる前に古い検証結果で次をマージしない。
2. 最新 default branch を取得し、必要なら `grape rebase` で追従する。競合は issue-runner に返す。`git rebase` で開始したり、grape の拒否を迂回したりしない。
3. base/head を確定して必要なテスト・レビュー・CI を再確認する。差分や base が変わった場合、影響に応じて再実行し、過去の合格をそのまま流用しない。
4. QA が自動マージ条件または対象に一致する人間承認と品質条件を確認する。GitHub の保護規則を守り、管理者バイパスで通さない。
5. 実行先で許可されたマージ方式を使い、可能なら期待 head SHA を条件に指定して競合更新を防ぐ。条件付きマージが使えなければ、同等の保護があることを確認できるまで保留する。
6. 実際のマージ結果と commit を確認してから issue を完了にする。自動マージの予約だけでは完了にしない。途中失敗時は GitHub の実状態を照合してから再試行する。

push は `grape push`、自身が作った issue/PR の無確認編集は利用先の規則で指定された安全なラッパーを使う。使用可能かを確認し、拒否・未導入の場合は直接操作へ自動フォールバックしない。外部操作の権限確認が必要なら、その操作だけを待機させる。

共有資産に変更がある issue は、別 worktree でも競合し得る。Pdm が所有範囲を調整し、前の issue のマージ後に割り当てる。worktree とブランチの削除は自動完了条件に含めず、利用先の削除規則に従う。

## 終了

ゴールの達成条件ごとに、マージ済み PR・検証済みレポートなどの根拠を対応づける。全条件を満たして初めてゴールを完了にする。全件が承認待ち・blocked なら状況と解除に必要な入力を報告する。単なる停止やセッション終了を完了と記録しない。

報告は完了項目・成果物・検証・残りの承認待ちと保留・次の再開点を含める。追加改善は提案として残し、達成済みゴールの作業を延長しない。会話外の常駐や定期実行は、別の実行基盤が確認できない限り約束しない。
