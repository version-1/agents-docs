# Lego Programming

実装対象を、責務・入力・出力・副作用・依存方向を説明できる部品として組み立てる。小さなファイル化が目的ではなく、変更理由の違うものを混ぜず、既存の構造・命名・公開契約に自然に置くための判断基準である。

## 進め方

1. 今回の部品を少数の責務として言語化し、所有状態と外部 I/O、依存方向を確認する。UI、業務判断、取得、永続化、表示を不用意に混ぜない。
2. 既存の類似部品を再利用・拡張できるか検討し、各部品を一つの変更理由と、内部手順を漏らさない contract にする。
3. 上位部品は下位を調整し、変換・検証・保存・表示などの接続点を明示する。組み合わせが肥大化すれば、それも責務を持つ部品にする。
4. 実装後またはレビュー時に、名前、配置、依存方向、テスト単位を見直す。呼び出し側が内部状態や手順を知りすぎていれば境界を直す。

## 判断基準

良い部品は、関連する状態とロジックがまとまり、呼び出し側が内部構造へ依存せず、同じ contract の別実装へ置き換えやすく、I/O・時刻・乱数・グローバル状態を境界に分けられる。既存レイヤーと配置・命名も一致させる。

取得・変換・検証・保存・表示を一箇所で担う、引数が増え続ける、分岐や変換がコピーされる、無関係な setup が多い、`manager`、`helper`、`utils`、`common` のように責務が曖昧、という兆候は境界を見直す。再利用のためだけの過剰な抽象化はしない。

一般に Handler/Controller は protocol、UseCase/Service は操作の orchestration、Domain は不変条件、Repository/Client は外部境界、Mapper/Presenter は変換を担当する。フロントエンドでは Page/Route が組み立て、Layout が配置、Feature が UI ワークフロー、Hook が状態・副作用、API Client が I/O、ViewModel が表示変換を担う。既存プロジェクトの語彙を優先する。

実装は `code-general`、言語別判断は該当する `code-*` を併用する。大きな React 分割は `component-design`、命名は `code-naming`、差分レビューは `code-review` を併用する。完了前に、主な部品の責務、入出力・副作用・依存先、上位からの隠蔽、既存構造との整合、変更理由の分離、境界に沿った検証を説明できることを確認する。
