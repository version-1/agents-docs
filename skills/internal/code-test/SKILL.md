# テスト設計

変更で壊れると困る仕様を、維持可能な観測としてテストする。カバレッジや実装の写しではなく、壊れやすい領域を優先する。

## 層の役割

- **Unit**: 純粋ロジック、ドメインルール、境界値。DB・ネットワーク等の依存を除く。
- **Integration**: DB、キュー、キャッシュ、外部 client を含む接続、query、migration、transaction、整合性。
- **E2E**: 重要な利用者フローを最小本数で扱う。遅さと不安定さを考慮する。

同じ保証を全層に重複させず、ルールは Unit、接続は Integration、重要フローは E2E に置く。

## 観点と設計

対象ごとに、代表的な正常系、空・最小・最大・上限超過・ページ境界等の境界、validation/認証認可/依存失敗/DB 失敗を選ぶ。必要に応じて、冪等性、transaction、競合更新、公開 contract の互換性、失敗時のログ等の可観測性、N+1 や大量件数を検討する。

観測可能な入力・出力・状態変化を assert し、内部呼出順・private な構造へ依存しない。AAA と一つの主張を保ち、分岐はケース名付きの表駆動で扱う。フィクスチャは目的に対して最小にし、複雑な期待値計算や条件分岐をテストへ持ち込まない。

sleep を避け同期手段を使い、時刻は固定・注入、乱数は seed 固定、共有 DB・グローバル状態を分離して flake を防ぐ。モックは失敗再現に用い、作り込みすぎない。DB、メッセージング、認可など重要な境界は統合テストでも確認する。

バグ修正では再現条件を小さく定義して回帰テストを加え、仕様変更なら仕様の明文化も検討する。失敗理由が不明、実装変更だけで壊れる、遅い・不安定なら、assert、境界、層を見直す。
