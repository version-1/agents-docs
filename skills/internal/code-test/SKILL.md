# テストの評価基準

良いテストは、保証する仕様を壊せば失敗し、仕様を維持する内部変更や正常な追加では壊れない。期待値は仕様、公開 contract、具体例を根拠に、対象の実装とは独立に定める。対象と同じ計算で期待値を作って自己検証しない。カバレッジや実装の写しより、この性質を優先する。

## 五つの評価軸

### 1. 何を保証するか

- **良い状態**: 対象、前提、準備、期待結果が読み取れ、失敗がどの仕様違反かを示す。
- **NG 兆候**: テスト名や assert だけでは前提・期待する契約が分からない。
- **改善**: 入力、操作、観測する結果を仕様の言葉で明示し、不要な準備を除く。

### 2. 読みやすいケース

- **良い状態**: 上から読んで、必要な入力・操作・結果が追える。結果を左右する条件はテスト本体にあり、fixture は背景データに留まる。
- **NG 兆候**: 巨大 fixture や helper をたどらないと条件や期待値が分からない。
- **改善**: ケース固有の条件を近くに置き、fixture を最小化する。共有 helper は意味のある操作だけにする。

### 3. 診断できる失敗

- **良い状態**: 一つの振る舞いを主題にし、ケース名と失敗出力から条件・期待・実際が分かる。関連する複数 assert は許容する。
- **NG 兆候**: 無関係なシナリオが混在する、または巨大な差分だけが失敗理由になる。
- **改善**: 振る舞いごとに分け、比較結果に契約上重要な差を絞る。一律の一 assert や AAA コメント強制はしない。

### 4. 再現可能であること

- **良い状態**: 同じ条件なら同じ結果になり、時刻、乱数、外部依存は必要に応じて固定・注入・制御される。
- **NG 兆候**: 固定 `sleep`、現在時刻、未制御の乱数やネットワークに頼る。
- **改善**: 同期の完了条件を待ち、clock や seed、依存の境界を制御する。実 DB を一律に避けず、接続や transaction の contract には Integration を選ぶ。

### 5. 他のテストから独立すること

- **良い状態**: 単独実行、順序変更、対象が対応する並列実行でも、他テストの残存状態に左右されない。可変共有状態は隔離・cleanup し、読取専用 fixture は共有できる。
- **NG 兆候**: グローバル状態、共有 DB、環境変数、ファイルを復元せずに残す。
- **改善**: テストごとの名前空間、cleanup、明示的な初期化を使い、並列化は対象が対応する場合にだけ行う。

## 補助となる判断

Unit はルール・境界値、Integration は DB・キュー・認可など境界の contract、E2E は重要な利用者フローを最小本数で保証する。同じ保証を全層に重複させず、代表正常系、異常系、境界を選び、必要に応じてデータ整合性や互換性を扱う。

固定値や snapshot は、仕様として決まった上限・形式・互換 contract を表すなら適切である。一方、現状の偶然の件数や内部構成を固定する期待値は避ける。モックや fixture も一律に禁止せず、失敗再現、境界の制御、読みやすい前提のために必要最小限に使う。

バグ修正では再現条件を小さくして回帰テストとして残す。AAA は読みやすさに役立つ場合に使うが、形式より五つの評価軸を優先する。
