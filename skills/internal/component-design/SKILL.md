# Component Design

React UI を変更・テストしやすい責務境界へ落とし込む。細分化自体が目的ではない。

## 適用と併用

新規画面、画面へのまとまった UI 追加、大きな JSX の分割、既存部品の探索・再利用、複数要素を段階実装する場面で使う。文言・色・余白だけ、または境界が明確な小修正には使わない。実装は `code-general`、React の実装判断は `code-react`、テストは `code-test` を併用する。欠陥レビューは `code-review` を優先する。

## 設計の進め方

1. 近い画面から、配置・命名・部品粒度、UI/フォーム/取得/状態管理、Server/Client Component、アクセシビリティとテストの既存パターンを確認する。
2. Input から画面目的、主要操作、情報優先度を読み、ページ、領域、セクション、繰り返し要素、操作部品のツリーを作る。仕様、空・読込・失敗・権限状態の未確定点を明示する。
3. ノードごとに表示責務、props、所有状態、イベント、依存データを仮置きし、既存部品候補と新規部品を分ける。
4. 未実装要素を一つずつ、既存部品の利用または公開 props・型を先に定めた新規部品として実装する。完了後に残要素と契約を見直す。

分担するなら、コンポーネント境界に沿って書込み範囲、props 契約、表示・状態、配置先、検証方法を渡す。

## 境界と契約

- **Component** は表示構造と操作の受け口を担い、複雑なドメイン判断、I/O、変換を抱え込まない。分岐が表示パターンを表すなら部品を分ける。
- **Hook** は画面固有の状態遷移、派生値、イベント手続き、副作用をまとめる。API 等は既存の service 層または hook に置き、描画が使える戻り値にする。早すぎる汎用化はしない。
- **View model / 純粋関数** は API・ドメイン型と表示の境界に置く。整形、ソート、グループ化、空状態判定を React から分離し、API 型、フォーム値、表示値を安易に兼用しない。
- **イベント** は操作の意味を表す名前にし、子へ渡す callback は外部契約として発火条件と値が分かる型にする。
- props は必須・任意と禁止状態を型で表す。boolean が増えるなら variant や union を検討し、曖昧な `data` や `item` を避ける。

分割は行数でなく変更理由で判断する。表示・取得・検証・権限・整形の混在、重複 JSX、追えない状態更新、UI パターン別の分岐、DOM 前提のロジックは分離の合図である。一方、props を通すだけの層、名前の弱い薄い部品、移動を増やすだけの分割は避ける。

## 状態と代表的な画面

状態は最小の所有者に置く。局所 UI は local state、URL と同期する条件は既存 router、サーバー状態は既存の data fetching、複数画面共有だけを既存 store/context に置く。派生値は重複保持しない。

フォームは値、検証、送信 payload、表示を分離し、validation error、server error、送信中、成功を区別する。一覧や詳細は loading / empty / error / success と操作を混ぜず、重い変換・権限判断を純粋関数へ出す。性能施策は必要なときだけ導入する。

button と link、label と input、icon button の accessible name、複合 UI の focus・キーボード操作を既存 UI ライブラリに沿って守る。

## 検証と出力

表示分岐と操作は利用者が観測する文言・role・label・状態変化で、変換と状態遷移は純粋関数または hook で検証する。既存の mock 方針に従い、private な構造へ過度に依存しない。

完了前に、境界・props・型境界、状態、アクセシビリティ、既存 UI との一貫性、未実装要素を確認する。最終報告には、分けた境界、契約と状態管理、検証、残る未検証事項または分割候補を示す。
