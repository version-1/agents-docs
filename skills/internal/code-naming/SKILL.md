# Code Naming

命名だけを扱う。責務、抽象度、既存語彙、呼び出し側の読みやすさを基準に、第一候補と原則 3〜5 件の候補を示す。設計全体、バグ、仕様違反、typo の検査は目的外である。

## 基準

- 周辺のディレクトリ、ファイル、型、メソッドが伝える文脈を重複せず、既存の命名規則・ドメイン語彙・prefix/suffix を優先する。局所的な短さより体系を壊さないことを優先する。
- 簡潔だが抽象的すぎない名前にする。実装詳細は隠す一方、境界、永続化方式、外部 API、非同期性など利用側の判断に必要な語は残す。
- `Manager`、`Handler`、`Processor`、`Service`、`Util`、`Data`、`Info`、`helpers`、`utils`、`common` は責務を絞れないなら避ける。略語は定着したものだけにする。
- Boolean は肯定形、関数・メソッドは意味のある動詞句、型・class・interface は利用側が依存する役割を表す名詞句にする。単位、時刻基準、上限、状態遷移の向きが重要な値は名前に含める。
- ディレクトリとファイルで概念を重ねず、一方に文脈を担わせる（例: `user/repository.go` または `repository/user.go`）。

対象名、責務、スコープ、呼出側と既存パターンを確認し、名前に残す情報、周辺に任せる情報、隠せる実装詳細を分ける。名前の変更で解決しない責務混在なら、候補より先にその懸念を示す。

単一名は「おすすめ、短い理由、代替案と適する条件、注意点」で、複数名は「現在名・推奨名・理由」の表で出す。実装やリネームは `code-general`、バグ等のレビューは `code-review`、次の開発者の理解全体は `code-next-developer-review` を併用する。
