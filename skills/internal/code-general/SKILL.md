# Code General

既存コードベースの機能追加、修正、リファクタリングを、小さく意図が明確な差分にする。言語・フレームワーク固有の判断は該当する skill を併用し、レビューだけなら `code-review` を優先する。

## 優先順位

1. 仕様、公開契約、データ互換性を壊さない。
2. 既存の構造、命名、責務分割、エラー処理に合わせる。
3. 変更を必要最小限にする。
4. 保守性、テスト容易性、調査容易性を損なわない。

最小変更が責務混在やテスト不能を固定化するときだけ、理由を説明できる小さな構造改善を含める。大きな設計変更は実装前に方針を整理する。

## 進め方

1. 関連コードとテストを読み、変更すること・しないこと、同じ責務の置き場所、入出力・エラー・永続化・外部 I/O の契約、検証方法、固有規約と生成物を確認する。
2. 不明点は既存実装・テスト・命名から確認し、それでも決まらなければ仮定を明示して最小の判断にする。
3. 既存パターンに沿って実装する。ドメイン判断、状態、I/O、表示、永続化を混ぜず、型/API/エラーの contract を厳密にし、関数を単一意図に保つ。増える分岐は責務別の型・関数・interface へ戻せないか検討する。
4. formatter、静的検査、テストを実行し、差分から不要変更、責務混在、命名の違和感、検証漏れを除く。

Go は `code-go`、TypeScript は `code-ts`、React は `code-react`（必要なら `code-ts`）、Ruby/Rails は `code-ruby`、CSS は `code-css` を併用する。命名に迷えば `code-naming` を使う。

完了前に、変更意図、スコープ、既存構造との整合、重要な正常・異常・境界の検証を説明できることを確認する。最終報告は変更内容、主要な変更ファイル、実行した検証、未実行の検証または残る risk、使用 skill を簡潔に示す。
