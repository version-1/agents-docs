# Code Next Developer Review

数週間後の自分、初見のメンバー、障害対応者、類似機能の追加者が安全に変更できるかを評価する。今のバグより今回の変更で増えた迷いやすさを優先し、実装者の説明やテストを鵜呑みにせず、前提が崩れる状況を想定する。欠陥や重大リスクは `code-review` 観点として分ける。

## 進め方

差分の概念、責務、型、設定、テストを把握し、次の開発者が行う作業を2〜3件想定する。どこを読んで変えるか、守る前提が型・命名・テスト・コメント・文書に残るかを確認する。必要な観点だけ `references/next-developer-axes.md` を使う。

指摘は、具体的な開発シナリオ、今回の差分にある原因、迷うファイル・型・関数・テスト・文書、放置時の変更漏れ・誤用・重複・調査/レビュー費用を示せる場合だけ出す。好み、既存の読みにくさ、シナリオのない不安、実装案の決め打ちは避ける。

## 重要度

- **High**: 安全に変える必須前提が読めない、追加箇所が散らばり変更漏れが起きやすい、契約・境界の曖昧さが公開挙動やデータを壊しうる、検証・再現手順がない。
- **Medium**: 命名・配置・テスト・コメント・暗黙ルールにより理解、追加、調査が明確に難しい。
- **Low**: 小さな整理で迷いを減らせ、後続課題で十分なもの。

## 出力

1. **次の開発者が困る点**: 重要度、ファイル・行、シナリオ、根拠、影響、改善方向。
2. **次に行いそうな作業**。
3. **足りない手がかり**: 型、命名、テスト、コメント、文書、検証手順。
4. **通常レビューへ回すべき即時リスク**: 見つけた場合のみ。
5. 短い要約。

なければ「次の開発者が困る観点での重大な指摘はなし」と、確認範囲と残る不確実性を示す。パッチ作成や通常の欠陥・設計レビューと混同しない。
