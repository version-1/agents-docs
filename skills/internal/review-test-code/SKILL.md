## 目的

PR のテスト差分が変更契約を観測できているかを、ケース単位でレビューする。`format-test-cases` を使い、条件、入力、操作、実際のアサーション、根拠をケース表として先に整理する。必要に応じて `code-review` と `code-test` の観点を併用するが、同じ指摘を繰り返さない。

既定では静的レビューを会話内に出力する。レビュー依頼だけでは、PR コメント投稿、approve、request changes、修正、checkout、作業ツリーの変更を行わない。

## 対象と読み取り範囲

- PR 番号・URL・ローカル差分など、依頼で指定された対象と形式に従う。PR では base と head を確認し、`merge-base(base, head)..head` の意図で比較範囲を定める。
- 追加・変更・削除されたテスト、fixture、helper、共通 setup、mock を読む。それらの変更で影響する既存ケースと、削除によって失われる保証も対象に含める。
- 本体差分、公開契約、仕様が利用可能なら照合する。テスト名や実装の期待値を写しただけの記述から、正しさを断定しない。
- 巨大な PR は抽出した対象と未確認範囲を明記し、表には確認した全ケースを追跡する。

## ケースごとの評価

各ケースについて、「どのような誤実装・回帰ならこのテストを通過できるか」を具体的な反例で検討する。必要に応じて次を確認する。

- Arrange-Act-Assert が対象の変更へ到達し、期待した振る舞いを観測しているか。
- アサーションが十分に具体的か、期待値の根拠が契約や仕様にあるか。
- 例外、非同期処理、失敗経路、mock 境界、テスト隔離、時間・共有状態による flake を見落としていないか。
- 不足を指摘する前に、変更契約に対するリスクと、既存の別テストで既に検証されていないかを確認する。

一律のケース数、coverage 目標、assert 数は課さない。静的レビューの結果とテスト実行の結果を区別し、実行していない場合に成功を断定しない。

## 出力

依頼された形式がなければ、次の順で出力する。

1. **指摘一覧**: High、Medium、Low の順に、指摘 ID、ケース ID、`path:line`、問題、具体的な反例、影響、必要な検証を記載する。根拠が足りないものは `確認不能` として分ける。
2. **ケース別レビュー表**: `format-test-cases` の表を基に、変更種別、評価、指摘 ID を追加する。評価は `指摘あり`、`指摘なし`、`確認不能` など、確認結果と分かる表現にする。`指摘なし` は保証を意味しない。
3. **不足ケース・不明点**: 変更契約とリスク、既存テストの確認状況を添える。
4. **対象範囲と検証**: 比較範囲、抽出・未確認範囲、実行した検証と未実施を簡潔に記載する。
