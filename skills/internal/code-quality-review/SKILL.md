# Code Quality Review

通常の欠陥検出ではなく、継続的に変更、テスト、理解、運用できるかを評価する。実装者の説明、既存テスト、metric を鵜呑みにせず、構造、責務、契約、依存、検証可能性、観測可能性への実際の影響を調べる。

## 対象と進め方

対象は実装済みの差分、PR、コミット、指定範囲。差分と関連する責務、データ、依存、テストを把握し、提示された metric や CI 出力を先に読む。なければ安全に確認できる既存の検証結果だけを使う。`references/quality-axes.md` から今回に効く観点だけを選び、品質低下がどの将来作業を難しくするか具体化する。即時欠陥は通常レビューへ分ける。

## シグナルと評価

complexity、関数長、ネスト、重複、fan-in/out、coverage、lint/static analysis は候補を見つける補助証拠であり、数値だけで重大度を決めない。未計測なら数値を作らず `未計測` とし、必要な追加検証を示す。生成コード、parser、状態機械、互換 adapter など高くなりやすい領域は理由を確認する。

評価は変更・テスト・調査のしやすさで行う。`Critical` は安全な変更や検証を大きく阻害、`Major` は保守・レビュー費用を明確に増加、`Minor` は小さな整理で改善できるもの。必要なら総合を `A`（懸念ほぼなし）〜`D`（先に構造改善・テスト補強を要検討）で示すが、根拠と優先度を必ず添える。

指摘は、対象範囲の根拠、将来の影響、読み・変更・テスト・調査のどれを難しくするか、改善方向を示せる場合だけ出す。好み、無関係な既存不満、根拠のない設計批判、詳細すぎるパッチ案は避ける。

## 出力

次の順で、必要な項目だけを出す。

1. **Quality Summary**: 総合評価と主なリスク。
2. **Quality Signals**: `Signal / Result / Interpretation / Action`。未計測も明示。
3. **Scorecard**: 必要な観点の A–D と根拠。
4. **Findings**: `Critical / Major / Minor`、ファイル・行、根拠、関連 signal、将来の影響、改善方向。
5. **Quality Gate**: merge 前、follow-up、対応不要。
6. **通常レビューへ回すべきリスク**: 見つけた場合のみ。

指摘がなければ「品質レポート観点での重大な指摘はなし」と、確認範囲・残る不確実性・評価根拠を示す。点数や metric で実装者を裁かず、次の判断に使える根拠を残す。
