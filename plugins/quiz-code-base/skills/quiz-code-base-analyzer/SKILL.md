# 大目標

定期的に、設計・レビュー時の認識と実際のコードの振る舞いのズレを見つけ、認識を修正する。

## 解析と作問

- 指定範囲に関係する振る舞いを出題する。正解の裏付けに必要な関連コード・DB定義・呼び出し元は範囲外も読む。
- 優先する題材: データのリレーション、外部キー・削除連動、必須・一意・値域制約、その保証層（DB／モデル／API）、検証を迂回する更新経路、権限チェック、トランザクション境界、副作用、分岐・例外時の動作。
- 「この設計判断は成立するか」「この更新経路で何が保証されるか」のように、具体的な前提・経路・条件を問題文に含める。単なる名前・行番号・構文の暗記を目的にしない。
- 正解は現在の実装で一意に裏付ける。ドキュメントを正解の代わりにしない。実装だけでは断定できない場合は作問しない。静的解析から本番DBの適用状態を断定しない。
- 選択肢は重複しない4つ。正解は1つ。誤答は、層の混同、暗黙の連動・保証の想定など実際にあり得る思い込みから作り、それぞれの誤りを説明する。「すべて正しい」、複数正解、好みで決まる設問を避ける。正解だけ長い等の手掛かりを減らす。
- 根拠の全ファイル（重要な呼び出し元や比較した文書も含む）、行・シンボル、解説、レビュー上の注意点、不一致時の整合提案を保存する。秘密情報を問題に転記しない。

## 保存・再確認

[問題入力契約](../quiz-code-base-recorder/references/cli.md) に従いJSONを作り、共通CLIの `add --input FILE` で保存する。根拠ハッシュはスクリプトが採取する。意味の同じ問題の量産を避け、`list` で既存の題材も確認する。

`select` が `needs_review` を返した場合は `inspect --id ID` で旧問題を読み、根拠と関連コードを再確認する。
- 正解・解説に影響しない変更: `refresh --id ID`。削除済みファイルを根拠から外す等の契約変更は refresh で誤魔化さない。
- 正解・解説に影響する変更: 修正版JSONを `revise --id ID --input FILE`。旧版は履歴付きで保管し、新版は未出題・連続正解数0。
- 根拠不足: `delete --id ID` で出題対象から除外し、理由をユーザーに示す。

AIが意味の検証を担当し、ハッシュ確認・構造検証・保存はCLIに任せる。候補全件のコードを毎回読み直さない。
