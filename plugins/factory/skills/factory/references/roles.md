# 役割契約

これは factory のタスク別役割であり、同名の登録済み agent の存在を前提にしない。実行先のモデル規則と利用可能な agent に合わせて、役割と下記の契約を指示として渡す。モデルが指定されていて利用できない場合は、別バージョンを使ったと偽らず制約を報告する。

初期提案の `refinener` と `documentor` は互換のため役割名として維持する。

追加指示の取り込み、役割間の連絡、判断のエスカレーションは[指示・連絡とエスカレーション](communication.md)に従う。

## Issue ごとの担当と引き継ぎ

- 1 issue に1人の issue-runner を割り当て、完了まで責任と状態を維持させる。保留中は再開できる状態を保存する。verifier、refinener、QA はその issue の工程ごとに専任担当を起動し、複数 issue の成果物や判断を同じ担当の文脈に混在させない。
- 同一 issue は implementer、verifier、refinener、verifier による再検証、QA の順に進める。verifier が依頼する独立した reviewer は並行できる。issue 間は最大5件まで並行できるが、依存または変更範囲の衝突がある場合は直列化する。
- 全役割を常駐させない。工程を終えた担当は、次の担当または再開担当が作業を再現できる状態を残して終了し、agent 枠を解放する。再起動時も担当を入れ替えたことだけで改善の回数や保留の履歴をリセットしない。
- 引き継ぎには issue、受け入れ条件、worktree とブランチ、base/head SHA、成果物、実行した検証と結果、未解決指摘、再試行回数、次の工程または保留理由を含める。

## Pdm

- ゴールの達成条件に対して、現状との差分・必要タスク・依存関係・優先度を決める。既存 issue を調べて重複を避ける。
- 優先度は達成条件への寄与、依存を解放する効果、リスク、期限から判断し、理由を残す。
- 実行可能な issue を最大5つの issue-runner に割り当てる。担当・変更範囲を一元管理し、同一 issue の二重割り当てを防ぐ。
- 承認待ち・保留から独立した仕事を進める。依存が循環する場合は分割を見直す。
- ゴールの完了を、issue の件数でなく達成条件と根拠で判定する。
- [引き継ぎと QA](handoff.md) に従い、次担当・開始確認・停滞・レビュー枠を管理し、QA 後の Ready 化と直列統合まで次アクションを確定する。

## issue-runner

- 受け入れ条件を理解し、PR・調査レポートなどの成果物を完成させる責任を持つ。
- 専用 worktree・ブランチと変更範囲を確定し、implementer、verifier、refinener の受け渡しを管理する。
- レビュー結果、修正、再検証、SHA、保留理由と [Issue ごとの担当と引き継ぎ](#issue-ごとの担当と引き継ぎ) の必要情報を issue に記録する。
- implementer の自己申告だけで完了にしない。QA に最終成果物と検証根拠を渡す。
- 各工程終了時に [handoff 記録](handoff.md#各工程の-handoff) を揃える。依頼送信と実行開始を分離し、Pdm に担当の実状態を渡す。

## implementer

- コード調査、実装、ドキュメント、調査レポートなど、issue に必要な作業を行う。
- 変更範囲と受け入れ条件に合った検証を実行し、成果物・差分・実行結果・未確認点を verifier へ渡す。
- verifier が集約した Medium 以上の指摘を修正する。指摘に反証がある場合は根拠を返し、verifier の再判定を受ける。
- Low は記録して進められるが、深刻度を下げてゲートを回避しない。

## verifier

実装とは独立した、この issue 専任の担当が検証する。各 reviewer には同じ issue・最終差分・base/head SHA・検証結果を渡す。

| Reviewer | 起動条件 | 観点 |
|---|---|---|
| code-reviewer | コード変更 | 仕様適合、回帰、境界条件、公開契約、テストの有効性 |
| ui-reviewer | 画面や表示の変更 | 実際の描画、画面幅、各状態、視認性、アクセシビリティ |
| ux-reviewer | 画面やユーザーフローの変更 | 目的達成、操作導線、エラー・空・待機状態、取り消しや回復 |
| security-reviewer | 機密情報、外部入力、権限、認証、外部通信などの変更 | 信頼境界、情報漏えい、入力検証、権限逸脱、依存関係のリスク |

- 純粋な調査や文書 issue でも、根拠・正確性・受け入れ条件を独立に検証する。
- 省略する reviewer は理由を記録する。必要な UI の実表示確認や必須検証ができない場合は、未確認として保留し、合格扱いにしない。
- 全担当の結果を待って重複と矛盾を整理し、implementer に一つのフィードバックとして返す。
- 指摘は ID・深刻度・場所・問題の根拠・影響・確認方法を含む。High は重大な機能破壊や安全性・データの問題、Medium は受け入れ条件や通常利用に影響する欠陥、Low は完了を妨げない改善とする。
- 棄却は反証と理由を記録する。未解決件数を減らすための棄却をしない。
- refinener 後は変更に応じたテストとレビューを再実行する。レビュー範囲と SHA を記録する。

## refinener

この issue 専任の担当が、検証済みの成果物を1巡だけ改善する。必要な refactor と documentor を起動し、改善が不要ならその理由を残す。実装範囲や仕様を広げず、issue-runner に差分と挙動維持の根拠を返して再検証へ送る。

### refactor

PR の差分を中心に、理解しやすい責務分割、簡素化、必要な共通化を行う。挙動、公開契約、受け入れ条件を維持する。挙動変更が必要なら改善として混ぜず、Pdm に別判断を返す。

### documentor

変更と文書の整合、必要な文書更新、入口からの導線を確認する。プロジェクト全体との不整合を調べるが、この issue に必要な文書だけを更新し、無関係な全体再編は提案に留める。

## QA

- この issue 専任の担当が、最終成果物を達成条件と照合し、テスト・レビューの証拠と対象 SHA を確認する。
- コードや文書を直接修正せず、不備は issue-runner に返す。
- [QA の最終出力](handoff.md#qa-の最終出力) を必須とし、品質・Draft / Ready・merge 承認・配布公開承認・自動統合可否を別々に判定する。block ごとに owner と解除条件を渡す。
- PR を作らない調査 issue は、検証と評価が合格なら成果物へのリンクを残して完了にする。調査結果が要求するプロダクト判断は別の承認待ち項目にし、決定済みとは扱わない。
