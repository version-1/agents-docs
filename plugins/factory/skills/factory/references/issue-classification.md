# GitHub Issue の分類と関連付け

Pdm は管理 issue・作業 issue の作成、取り込み、再開時に本規定を適用する。分類は実行対象や進め方を表し、採用判断・品質確認・人間承認を代替しない。

## 役割と正本

| 項目 | 表現する情報 | 運用 |
|---|---|---|
| Labels | factory の対象、作業の種類、対象領域 | `factory` 必須。種類は原則1つ、領域は必要に応じて複数 |
| Projects | 進行状態、優先度、GitHub 上の担当者 | 既存設定またはユーザー指定がある場合に使用 |
| Milestone | リリースや期限のある達成目標 | 既存設定またはユーザー指定があり、達成に必要な作業 issue に付与 |
| Relations | 作業分解の親子関係、実行順序の依存関係 | GitHub の sub-issues と blocked by / blocking で設定 |

Projects 使用時はそのフィールドを状態・優先度・担当の正本とし、未使用時は issue 本文を正本にする。詳細工程、内部 agent 名、判断理由、検証根拠は本文に記録する。Relations を関係の正本とし、本文の一覧やリンクは参照・説明として整合させる。同じ情報を別のラベルで管理しない。

Projects・Milestone が未設定なら、必要性と構成を提案し、作成はユーザーの確認後に行う。未設定だけを理由に作業を止めない。

## Labels

- 管理 issue とすべての作業 issue に `factory` を必須とする。factory が作成する issue には作成時から付ける。
- ラベルなしの既存 issue は候補として参照するだけにし、自動でラベルを付けて処理対象にしない。ユーザーが対象として指定した場合に `factory` を付け、[取り込み判断](intake.md) を行う。
- 種類は `type:bug`、`type:feature`、`type:chore`、`type:docs` などを原則1つ付ける。領域は `area:audio`、`area:billing`、`area:ci` などを必要に応じて複数付ける。
- `bug` など同義の既存ラベルは再利用し、重複を作らない。ただし対象判定には名前が `factory` のラベルを使う。
- 状態・優先度・担当・リリースはラベルに持たせない。既存の無関係なラベルを一括削除しない。

開始・再開時、割り当て前、マージ前に `factory` の有無を再確認する。実行中に解除を検出したら新規作業と自動マージを止め、担当に中断を伝え、途中成果・工程・SHA・再開条件を記録する。管理 issue から外れた場合はそのゴール全体、作業 issue から外れた場合はその issue と依存する仕事を止める。独立した他のゴール・issue は継続できる。再付与後は実状態と採用条件を照合して再開する。セッション外の常時監視は約束しない。

## Projects

既存の同等フィールド・選択肢を再利用する。新規構成を提案する場合の標準は次のとおり。

| フィールド | 標準値・内容 |
|---|---|
| Status | Todo / In Progress / Blocked / Awaiting Approval / Done |
| Priority | P0（最優先）/ P1 / P2 / P3（低） |
| Assignees | GitHub 上の担当者。内部 agent 名は設定しない |

詳細工程の `ready` は Todo、`implementing`・`verifying`・`refining`・`reverifying`・`qa` は In Progress、`blocked` は Blocked、`awaiting-approval` は Awaiting Approval、`done` は Done に対応させる。既存の選択肢へ対応付ける場合も、対応と保留・承認待ちの解除条件を本文に残す。優先度の判断理由と内部 agent の担当は本文に記録する。

## Milestone

該当リリースや達成目標に必要な作業 issue のみに付与する。同じ管理 issue の配下という理由で一律に付けない。期限未定なら期日は空欄とし、推測しない。ゴールの管理 issue は作業分解の入口であり、Milestone をその代わりにしない。

## Relations

- ゴールの管理 issue を親、作業 issue を子として sub-issues に設定する。既存の親がある場合は勝手に付け替えず、確認する。
- 実行順序の制約は blocked by / blocking に設定する。親子関係だけでは順序や待機を意味しない。
- 依存先が未完了・保留なら依存する仕事を開始しない。循環依存は作業分割を見直す。
- 本文の `Factory goal: <管理 issue の完全な URL>` は外部取り込み先を指定する情報として維持する。Relations と矛盾すれば再評価し、リンクだけで関係設定済みと扱わない。

## 設定できない場合

権限不足・機能未対応などで必須の `factory` ラベル、親子関係、必要な依存関係を設定・確認できない場合、その issue の実装開始を保留する。管理 issue に問題がある場合は配下の割り当ても保留する。失敗した項目、理由、必要な権限やユーザー判断、解除条件を記録し、独立した他の issue は進める。既存の親の付け替え確認待ちも同様に扱う。本文へのリンク記載を代替の完了条件にしない。

GitHub 操作は実行先の権限・承認規則に従う。設定を提案しただけ、または API 呼び出しを試みただけで成功したと記録せず、実状態を確認する。
