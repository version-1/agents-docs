# 工程の引き継ぎと QA 判定

## 実行前の確認

Pdm は開始時に実行先の branch 命名規則、worktree 制約、`grape rebase` / `grape push` の policy、利用可能な agent と起動手段を調べる。branch 作成前に候補名が既知の許可条件に適合することを確認する。安全な確認方法がなければ未確認項目と必要な確認者を記録し、未確認の操作を実行可能と扱わない。確認のために rebase や push を試行しない。

拒否されたら Git へのフォールバック、policy の書き換え、拒否を逃れる rename は行わない。対象 branch・操作を限定して必要な例外承認を求め、承認内容と実行結果を記録する。以後の履歴変更は [進捗と承認](state.md) に従う。

## 各工程の handoff

implementer → verifier → refinener → verifier の再検証 → QA の各終了時に、送り手は次の記録を残し、Pdm が次担当と次アクションを確定する。QA 後も Ready 化・統合・承認待ち・修正への引き継ぎを同様に記録する。

| 項目 | 必須内容 |
|---|---|
| 対象 | issue / PR、終了した工程、成果物・差分へのリンク |
| 検証対象 | 固定した base SHA / head SHA。PR がない成果物も対象 commit と成果物の版を特定 |
| 受け入れ条件 | 条件ごとの合否・未確認、必要な native / 実機検証の結果 |
| 検証根拠 | 実行コマンド、実行環境、終了コード、raw log の保管先。要約だけで成功としない |
| 残件 | 指摘と深刻度、未完了作業、block 理由、解除条件 |
| 次の実行 | 次担当の owner / agent ID、次アクション、期待成果物、開始確認の期限または次の確認時点 |
| 承認 | PR merge と配布公開それぞれの人間承認要否、理由、対象 SHA / 成果物。未判定は明記 |

記録は GitHub の管理 issue / 作業 issue から辿れる場所に置く。機密情報を raw log に残さない。SHA や成果物が変われば必要な再検証を行い、旧結果や承認をそのまま転用しない。

## 割り当てと開始確認

Pdm は `依頼送信 → 割当受理 → 開始確認 → 完了` を区別して記録する。送信成功だけでは実行工程を進めない。

- 稼働中の担当への連絡には `send_message` を使えるが、idle / completed の担当を起動する効果があるとは扱わない。
- idle / completed の担当は、利用可能な `followup_task` または新規 `spawn` によって起動する。名称が異なる環境では同等の起動 API を確認する。
- 担当の開始 ack（対象と次アクションの受理）と、ツールが示す live / running 状態の両方を確認する。先に完了通知が来た場合は対象 SHA・成果物・検証根拠を確認して完了を受理できる。開始したと後付けで記録しない。
- 起動確認できなければ未開始のまま扱う。未完了の旧担当の実状態を照合し、停止または重複がないことを確認してから再割り当てする。起動 API がなければ必要な担当だけを保留し、メッセージを実行済みと扱わない。

## 停滞の検知と枠の配分

Pdm は担当からのイベント受信時、新規割り当て前、再開時、および設定した次の確認時点に、未開始・handoff 待ち・QA 後の未処理・保留を照合する。確認時点は作業と実行環境に応じて明記し、ユーザーの状況質問を契機にしない。会話外の監視は約束しない。

次担当なし、開始確認なし、確認期限超過、同じ残件のまま進展なしを検出したら、owner・最終進展・block 理由・次アクション・解除条件を記録して解消または保留する。外部承認待ちも解除判断の owner を特定する。ユーザーへの報告には停滞と必要な入力を含める。

agent の総枠には統括・reviewer・QA も含める。4枠なら少なくともレビューを実行できる1枠を確保し、必要なら統括を親が担う。新規実装や PR を増やす前に、検証・再検証・QA・Ready 化を待つ既存成果物を処理する。保留が他の独立作業を止める必要はないが、枠が埋まったままレビューを待たせない。

## QA の最終出力

QA は同じ base/head SHA と検証根拠に対して、次を別々に出力する。未確認を合格へ丸めない。

| 判定 | 出力内容 |
|---|---|
| 品質 | pass / fail / unverified。受け入れ条件、必須 CI、レビュー、native 検証、未解決指摘 |
| PR の状態 | Draft 維持 / Ready 化 / 既に Ready。残る実装・必須検証があれば具体的に記載 |
| merge の人間承認 | required / not-required / undetermined と理由、必要なら承認対象 SHA |
| 配布公開の人間承認 | required / not-required / undetermined / not-applicable と理由、対象成果物 |
| 自動統合 | allowed / blocked。現在の保護・権限・依存・競合・承認条件を含む判定理由 |
| 次の実行 | owner、Ready 化 / 直列統合 / 承認待ち / 修正等の次アクション、block ごとの解除条件 |

PR 作成、Ready 化、merge、配布公開は別のゲートとする。途中成果は Draft PR として共有できる。未完了実装や merge に必要な native 受け入れ条件が不合格・未確認なら Draft を維持して修正・検証へ返す。品質が pass で実装が完了した Draft は Ready 化へ進め、Ready 化した事実を確認する。merge の人間承認待ち、配布公開前の owner 判断、保護不足だけを理由に完成済み PR を Draft に残さない。

merge 承認は本体の承認対象変更と照合する。配布公開だけに必要な承認を merge 承認として扱わない。反対に、配布承認が済んでも merge 品質を免除しない。品質 pass・merge 承認不要または対象に一致する承認済みなら、保護を確認して [直列統合](state.md#マージと並行統合) へ渡す。

保護 API の 404、rulesets が空、必須チェックや merge queue の不足は品質や承認とは別の blocker として記録する。404 のみで「保護なし」と断定せず、権限不足や未確認も区別する。head と最新 base の保護を確認できなければ強制 merge、管理者 bypass、保護設定の自動変更は行わない。
