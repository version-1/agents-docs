# Factory

ゴールの達成条件を固定し、Pdm が計画から完了まで統括する。計画承認を挟まず、実行可能な仕事を継続する。

## 入力

- `/factory <goal>`: 新規ゴールを開始する。同じゴールがあれば既存状態から再開する。
- `/factory approve`: 一意に特定できる承認待ち1件に承認を適用する。対象が曖昧なら確認する。
- 停止・再開・方針変更は自然言語で受け付ける。停止時は新規割り当てを止め、実行中の担当にも中断を伝え、途中状態を記録する。再開時に実状態を照合する。

`skip` と `next` は設けない。承認待ちがあっても独立した issue を進める。

## 開始と権限

1. 実行先の AGENTS.md、プロダクト方針、既存 issue・PR、検証方法、GitHub の接続先、agent・モデル・並行数制限を確認する。
2. [進捗と承認](references/state.md) を読み、ゴールの管理 issue を作成または再利用する。達成条件・対象外・根拠を明文化する。曖昧さが達成条件やプロダクト判断を左右する場合だけ、推奨案を添えて一問ずつ確認する。
3. 各担当へ [役割契約](references/roles.md) の該当箇所と issue・受け入れ条件・作業場所・現在の SHA を渡す。

factory の実行依頼は、ゴール内の issue 作成・更新、PR 作成、検証、以下の条件付きマージを進める意図として扱う。ただしツール権限や上位の承認規則を拡張しない。必要な操作が拒否されたら理由を記録し、その操作だけを保留する。GitHub や委譲ツールが利用できなければ、実行したと装わず不足条件を報告する。

## 実行

Pdm → issue-runner → implementer → verifier → refinener → verifier による再検証 → QA の順に進める。

- Pdm は現状分析・必要タスク・依存関係・優先度を管理する。達成条件内の issue は随時追加し、既存方針内で必要な仕様を具体化する。ターゲット・料金・初期スコープ・期限などの方針変更や達成条件の拡張は人間へ戻す。
- issue-runner は最大5件を並行実行する。各 issue に専用 worktree とブランチを用意し、依存関係や共有ファイルの衝突がある仕事は直列化する。
- 実環境の agent 上限は reviewer 等も含めて守る。5枠を予約できるとは仮定せず、担当を待機・終了して空きを作る。必要なら統括役を親 agent が担い、レビューの独立性を保つ。未対応の agent 名やモデルを指定して起動したと装わない。
- verifier は必要な reviewer を選び、全結果を集約する。Medium 以上を修正し、対応必須の指摘がなくなるまで再検証する。
- 同じ原因で連続3回改善できなければ、試した対応と未解決点を記録して保留する。issue の作り直しや担当交代で回数をリセットしない。改善中なら続行する。
- refinener の品質改善は1巡とし、挙動を維持する。変更後は必ず再検証し、以後は指摘への修正だけを行う。

## QA と完了

QA は最終差分について受け入れ条件・検証・残存指摘・承認要否を評価する。自動マージは次をすべて満たす場合だけ行う。

- 受け入れ条件を満たし、必須 CI と必要なレビューが完了している。
- Medium 以上の未解決指摘がない。
- 課金・認証・データ削除／移行・外部送信・公開設定の変更を含まない。
- 既存プロダクト方針の変更を含まない。ゴール内の仕様具体化は許容する。

満たせない品質条件は修正または保留し、人間承認で免除しない。品質条件を満たすが承認対象の変更を含む PR は、具体的な最終成果物を提示して承認を待つ。

マージ操作・SHA 固定・再検証・レポートのみの完了は [進捗と承認](references/state.md) に従う。達成条件をすべて満たしたら停止する。全件保留なら理由と必要な入力を報告し、空回りしない。残りの改善案は提案として残す。
